---
name: new-migration
description: Add a new hand-numbered Alembic migration to the Buddyplan backend (SQLite, batch mode). Use whenever a change to backend/app/models.py alters the database schema or needs a data backfill.
---

Create a schema migration for: $ARGUMENTS

1. Look in `backend/alembic/versions/` for the highest `00N_*.py`. The new file is `00{N+1}_<snake_name>.py`.
2. Follow the header used in the existing migrations (e.g. `003_person_profile_color.py`):
   - A module docstring with one sentence describing the change.
   - `revision: str = "<file stem>"` and `down_revision` set to the previous file's stem. Don't use autogenerated hash ids.
   - `branch_labels = None`, `depends_on = None`.
3. Make the migration idempotent. `001_initial_schema` builds the schema with `Base.metadata.create_all` from the *current* models, so on a fresh database your new column or table already exists. Before adding anything, check with `sa.inspect(op.get_bind())` (`get_columns` / `has_table`) and skip if it's already there.
4. Run every column or constraint change inside `with op.batch_alter_table("<table>") as batch_op:`, because SQLite can't ALTER in place.
5. Do data backfills with `op.get_bind()` and `sa.text(...)`. Don't import ORM models, because they change over time. Small helpers from `app.services` are fine, as earlier migrations show.
6. Write a real `downgrade()` that reverses the change.
7. Update `backend/app/models.py` to match. `Base.metadata.create_all` runs after the migrations, so a mismatch fails silently for new tables and breaks on existing ones.
8. If the API shape changes, check the clients in `mobile_app/` (Dart models plus the Drift cache, which needs `build_runner`) and `dashboard_app/` (Kotlin data classes and Room).
9. Verify with `cd backend && docker compose up --build`. The migration runs at startup, so check the logs for `alembic` errors.
